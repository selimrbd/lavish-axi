Lavish · architecture

How Lavish works

Three processes, one mailbox on disk, and an HTTP request that is allowed to take an hour to answer.

There is no daemon to register with, no socket the agent has to be holding at the right moment, and no message bus. There is a small HTTP server on loopback, a JSON file on disk, and two clients that never speak to each other. Everything else in this document follows from that.

01Three participants

Your agent and your browser are both clients. Neither can be called; both call the server, whenever it suits them. The server is the only participant that remembers anything.

  • Your agent runs the lavish-axi CLI. It opens a session, it polls, it edits your HTML file on disk. Nothing can call it, so nothing is ever pushed to it.
  • The Lavish server is a detached Node process on loopback, spawned by the first CLI command that needs one and reused by every later command whose version matches.
  • Your browser loads the chrome page, which frames your artifact in a sandboxed iframe. The iframe has no same-origin access, so even the page you are annotating cannot reach the server directly — everything it wants to say crosses by postMessage and the chrome sends it on.

02The file path is the session

There are no session ids to carry around. The canonical path of your HTML file is the identity, and the key is derived from it:

sessionKey = sha256(realpath(file)).slice(0, 16)

Three consequences worth holding on to:

  • lavish-axi poll report.html is enough. The agent never has to have been told an id.
  • Two paths to the same file — a symlink, a relative path — collapse to the same session.
  • The key is derived, not secret. Anyone who learns the path can compute it, so the server never treats knowing the key as permission. The routes that put words in your mouth — queueing prompts, publishing a share, writing a whiteboard — additionally require a same-origin request, and every request's Host must be one this server answers to.

03Once around the loop

  1. lavish-axi report.html spawns or reuses the server, registers the session, and opens the browser at /session/<key>.
  2. The chrome frames /artifact/<key>/index.html. The only change made to your HTML is one appended <script> tag — the annotation SDK. Open the file directly and it is byte-identical apart from that.
  3. You click an element or select text. The SDK reports the target to the chrome, the annotation card opens, and the prompt is queued in the tab's sessionStorage. Nothing has left the browser yet.
  4. Send to Agent. The chrome POSTs the batch to /api/<key>/prompts. The server writes it into state.json and marks the session feedback.
  5. lavish-axi poll report.html returns that batch as JSON, with a DOM snapshot and a next_step string telling the agent what to do with it.
  6. The agent edits report.html on disk, like any other file.
  7. The server's watcher notices the write and emits a reload event over SSE. The chrome reloads the iframe and replays your scroll position and any half-written note.
  8. Repeat, until you or the agent ends the session.

Steps 4 and 5 are not synchronized with each other. Nothing about step 4 requires step 5 to have started, which is the whole subject of section 05.

04What a poll actually is

GET /api/poll?file=<absolute path>. That is all it is — an ordinary GET the server is allowed to answer late. It takes one of two branches:

Mail is waiting

The server reads the session, finds queued prompts (or a fatal artifact failure), removes them from state.json, and returns them. The request never waits at all, however long the mail has been sitting there.

The mailbox is empty

The server marks presence listening, registers a listener for this session's feedback and ended events, and holds the socket open. There is no timeout by default. It writes a whitespace byte into the response every so often so nothing along the way decides the connection is dead, then writes the real JSON body when the event finally fires. --timeout-ms exists for tests and debugging, not for the review loop.

05Can an agent start listening late?

Yes — at any time, from any process, with nothing lost.

Feedback is a mailbox, not a broadcast. An agent that was not connected when you pressed Send has missed nothing, because there was nothing to miss: what you sent was written to a file, not shouted down a wire.

Three properties make that true, and each is worth stating separately.

Queuing does not need a listener

POST /api/<key>/prompts writes your prompts into state.json and marks the session feedback. If an agent is long-polling, an event wakes it. If no agent has ever polled this session, the write is exactly the same write. The browser's side of the transaction is complete either way, which is why every feedback control stays live even while the panel is telling you that your agent is not listening.

A poll reads the mailbox before it decides to wait

The first thing /api/poll does is take whatever is queued. Mail from an hour ago comes back in the first milliseconds of the poll. The long-poll branch — the one that holds the connection — is only reached when the mailbox is already empty.

The mailbox outlives the processes

The server stops itself after 30 minutes with no browser and no poll connected (LAVISH_AXI_IDLE_TIMEOUT_MS), and when the last session ends with nothing attached it steps down immediately. state.json is untouched by that. The next lavish-axi poll spawns a fresh server, which reads the same file and hands over the same prompts. A different agent, a different terminal, a machine that has rebooted in between: the path is the identity, so the mail is still addressed correctly.

The fine print

Three rules bound the answer, and they are the ones that actually surprise people.

  • Delivery consumes. A batch is handed to exactly one poll and then removed. Two agents polling the same file split the mail between them rather than each receiving a copy, so read the response completely the first time. The one exception is a poll whose client disconnects while the response is in flight: the server puts the batch back, ahead of anything queued in the meantime, and marks nothing as delivered. Re-running an interrupted poll is always safe.
  • An ended session takes no new mail, but still delivers the old. Prompts queued before the end — including the browser's Send & end session, which posts the final batch and the end together — are handed to the next poll with session_ended: true. A batch posted after the end is refused, because no later poll would ever read it.
  • Presence is cosmetic. The browser is told whether an agent is attached and says so in the panel. It gates nothing.

06Presence, and what it does not mean

The chrome holds an SSE stream to the server and is told one of three states. All three are derived from live connections alone — never from what is queued, and never from session status.

State Means
waiting No poll is attached. The panel shows a line asking you to have your agent poll. Your feedback still queues normally.
listening A poll is holding a connection open right now. Anything you send wakes it within milliseconds.
working A poll took feedback and released. The agent is presumably editing. It returns to waiting when the agent posts a reply, or immediately if the batch ended the session.

07What can never wake an agent

Lavish runs a layout audit inside the artifact iframe on every render and reports what it finds to the server. That route deliberately never emits the event a poll waits on. Findings land in your Layout issues inbox and stay there until you select them and queue them, at which point they arrive at the agent as an ordinary prompt like any other. An agent cannot be woken by a machine's opinion of your layout — only by you.

The single exception is narrow and fatal: the artifact itself failed to load, or one of its subresources did. There is nothing to review in that case, so it is returned as artifact_failures without waiting for a human.

Detection is passive. Repair is requested.

08The other direction: live reload

The agent never pushes anything to the browser either. It writes the file, and the server notices.

Agent writesreport.html → Watcher fireschokidar, debounced → Server emitsSSE: reload → Chrome reloadsthe iframe only → State replayedscroll, open draft

Only the artifact file is watched by default. Watching whole directories saturated the event loop for artifacts living inside large trees, so directory watching is opt-in per artifact.

09What survives what

Event What happens
Browser refresh Session, queued prompts, layout inbox and your unsent annotation draft all come back. The inbox is re-bootstrapped from the server, the draft from the tab's own storage.
Closing the tab Nothing sent is lost. Presence drops to waiting. Anything you queued but never sent lived only in that tab.
Server idle shutdown The process stops; the session is untouched on disk. Session status is never changed by an idle shutdown, so the next open or poll resumes it.
Poll killed or timed out Undelivered feedback stays queued. Re-run the same poll command. The CLI prints that instruction to stderr on its way out.
You end the session Terminal. Every connected browser goes read-only at once. A plain re-open is refused; it takes an explicit --reopen.
The agent ends it Also terminal, but a later lavish-axi report.html revives it without a flag.

10Everything else, briefly

  • The sandbox. The artifact iframe runs without allow-same-origin, so it cannot read the chrome's DOM or call the server. Every message crosses by postMessage, stamped with the current load token.
  • Layout inbox. Findings are fingerprinted per rule, target and viewport class, and only a newer artifact load plus a complete audit at the same viewport can clear one. Not a closed drawer, not a queued fix, not an agent's reply.
  • Whiteboards. Mermaid diagrams become editable Excalidraw scenes in a second sandboxed frame. Scenes autosave to sidecar files; the Mermaid source in your HTML stays authoritative and there is no reverse conversion.
  • Image attachments. Content-addressed by their own hash. The iframe hands bytes to the chrome, the chrome uploads, and the server re-derives every authoritative field from disk, so a crafted prompt cannot aim an attachment at an arbitrary file.
  • Export and sharing. One transform inlines local assets into a single self-contained file, makes no outbound requests, and strips the SDK. Sharing publishes that file to a third-party host; local paths are redacted first.
